# ADR-0096: close the missing-round-content gap in the completion gate and auto-recovery

- **Status:** Accepted
- **Date:** 2026-08-20
- **Related:** ADR-0049 (`package_completion_blocking_defects()` — the shared structural-defect function this ADR extends), ADR-0093 (Richie/Regina Castellano — the first confirmed instance of this exact failure signature, fixed going forward via a token-budget bump), ADR-0094/0095 (the roster-*count* gap — a different, already-closed defect class; this ADR is about content completeness *within* rows that do exist), ADR-0052 (`invalid_role` sentinel), ADR-0085/0086 (the empty-character auto-recovery this ADR widens the trigger condition for, not the mechanism)

## Context

While remediating two live incidents (The Staged Suicide Details, The Birthday Betrayal — both 2026-08-19/20, see CHANGELOG), one character per package needed fixing beyond the missing-row problem ADR-0095 covers: Han Yu and Casey/Cassidy Chen each had a fully populated `description`/`background`/`character_role`, but **all 7 fields in their round-content call group** (`round2_questions`, `round2_script`, `round3_questions`, `round3_script`, `round4_questions`, `round4_script`, `final_statement` for detective style) were empty strings. Both were repaired individually via `regenerate-child-content`, verified against the live rows.

Investigated why neither the real-time completion gate nor any async detector caught this before a human noticed:

- First hypothesis (token-budget truncation, the exact mechanism ADR-0093 diagnosed for the character-style innocent-slip call) was checked against the **live** Make.com scenario via its API and ruled out: module 409 (the detective-route call) already runs at `max_tokens: 6000`, matching ADR-0093's own fix (`Child(Unified)35`, confirmed live and active, not merely drafted as CHANGELOG.md's stale note claimed). All Make.com execution logs for the relevant window report `status: success` — this is not a crashed run; the content silently doesn't get written despite Make.com reporting no error. Full per-module execution bundle detail isn't available through this session's API access (blocked by plan/log-retention scope), so the exact mechanism inside the successful-but-empty run remains unconfirmed.
- Read `package_completion_blocking_defects()` (the one function already wired into all three completion gates — the trigger, `heal_completed_packages()`, `promote_complete_packages()`) directly via `pg_get_functiondef`: it checks error bodies, invalid roles, meta-text leaks, self-directed questions, victim mismatch, slip-culprit leak, identity conflicts, and victim-playability — **nothing checks whether a character's round scripts or final statement are populated.** `validate_package_characters()`'s own inline `_empty_count` check is narrower still: `description IS NULL OR character_role IS NULL` only.
- The async "completed but empty" detector (`list_completed_but_empty_packages`, ADR-0043) only flags a package with **zero** characters total — not a package where every character row exists but some are missing their round content.
- The roster-count detector (ADR-0064) and the count-based recovery gate (ADR-0094/0095) both operate on character *count*, not per-field completeness — irrelevant here since the row exists.

**Net: no gate and no detector, real-time or async, checks this at all.** A character with this exact failure signature (identity fields fine, round content empty) has always been able to ship undetected.

**A prior attempt at this exact check already exists in the database, disconnected from every caller.** `get_empty_characters(p_package_id)` (migration `20260422125154_fix_get_empty_characters_to_check_scripts`) checks round-script/innocent/guilty/final-statement completeness by `mystery_style` — almost exactly this ADR's check, four months earlier. A full search (every function definition in `pg_proc`, the entire TypeScript codebase, every `.sql` file) found **zero callers** — not the completion trigger, not any edge function, not any cron, not the frontend. It has done nothing since the day it was written. That migration landed 2026-04-22 12:51 UTC; two of the worst-hit packages in this ADR's own historical sweep — "Death On The Dance Floor" (17/18 characters affected) and "Death At The Deadwood Saloon" (9/9) — were generated the **same day**, ~5 hours later. The shape of that timing (a fix written, apparently in direct response to noticing this defect, then never wired to anything) matches this codebase's own documented "guardrail built but never imported" failure class (memory `project_content_quality_detectors`). Not reused here — different design (`LENGTH < 50` threshold, joins `conversations` for `mystery_style`, a standalone `SETOF` rather than folded into the shared defect-list function) — this fix instead follows ADR-0049's established pattern of one function wired into all three completion gates. `get_empty_characters()` itself is left in place (unused, harmless) rather than dropped, since deleting it wasn't asked for and isn't necessary to close this gap.

**Historical sweep** (same discipline as ADR-0094's sweep, run directly against production): applied the proposed check read-only against every `completed` package. 21 packages / ~100 characters matched, ALL `is_paid = true`, `is_test = false`, dated between 2025-08-12 and 2026-04-22 — **none after** the 2026-08-11 token-budget fix (ADR-0093/`Child(Unified)34`). This is consistent with the historical cohort being the *same* pre-fix defect class ADR-0093 already closed going forward, never backfilled for the customers who received it before the fix shipped — not an ongoing pattern. Two additional hits were obvious dev/test rows (`TEST Mystery`, and detective-style rows with `title: null`, 3-4 characters, created seconds apart). **This historical backlog is explicitly out of scope for this ADR** — remediating ~100 characters across 21 real, some year-old, customer orders is a materially bigger decision (cost, customer communication, whether some warrant a different remedy entirely) than a completion-gate fix, and is flagged separately for a decision rather than bulk-actioned here.

## Decision

Add a `missing_round_content` defect class to `package_completion_blocking_defects()` — same layer ADR-0049 already established, avoiding a second, driftable copy of this check (this codebase's own documented "paired-predicate drift" failure class, memory `project_gate_detector_deadlock`). Widen `notify-generation-issue`'s `emptyCharacters` detection to match, so the *existing* re-fire mechanism (searchRows → update in place, 2-attempt cap, shared $10/day spend cap) auto-heals this defect class exactly as it already does for empty `description`/`character_role`, with zero new machinery.

**Field scope, evidence-matched, not maximal:**
- Detective style: `round2_script`, `round3_script`, `round4_script`, `final_statement` — generated uniformly for every character regardless of role (one call group, GROUP_ROUNDS_DETECTIVE), so an empty one is never legitimate.
- Character style: `round2_innocent`/`round3_innocent`/`round4_innocent`/`final_innocent` **and** `round2_guilty`/`round3_guilty`/`round4_guilty`/`final_guilty` — both branches are generated for every character (everyone might draw either slip); the historical sweep confirmed both branches fail together on the same character, not independently, consistent with a per-character write failure rather than per-call-group token truncation.
- `round2_questions`/`round3_questions`/`round4_questions` — shared field names across both styles, checked either way.
- **Deliberately excluded:** `round*_accomplice`/`final_accomplice`. That branch is conditional on `conversations.has_accomplice`; joining that in to avoid false-positiving on characters who legitimately never get it adds real complexity the historical sweep didn't verify against. Narrower, evidence-matched scope only — same discipline ADR-0094 used when it stuck to `extracted_characters` over `player_count`.

## Rationale

- **One function, three gates, for free.** `package_completion_blocking_defects()` is already called from the trigger and both recovery crons — this fix needed zero new wiring.
- **Verified against real data before shipping**, not just reasoned about: ran the new function definition read-only against `Death On The Dance Floor` (17 of 18 characters affected) and confirmed it correctly flags all 17 by name; ran it against both live-remediated packages and confirmed clean (`null`) — the new, stricter check doesn't regress the fix already shipped this session.
- **Reuses the existing auto-recovery mechanism rather than building a new one.** `notify-generation-issue`'s re-fire already handles both the "row is missing" and "row exists but is empty" cases (the same `CHILD_WEBHOOK` I used for the two live incidents' missing rows), already has attempt/spend caps tuned from a real 2026-08-11 incident (unbounded retries burning spend), and already suppresses the alert email while auto-recovery has budget left (`emptyCharacterRecoveryLooksClean`). Widening its *detection* condition is the whole change; the safety rails, cooldown, and grace-period logic around it are untouched.
- **Zero risk to existing data.** The trigger only fires on `generation_completed_at` transitioning `NULL → NOT NULL` — a one-time event per package, already fired for every historical package. The two recovery crons only touch packages currently in `needs_review`. Deploying this migration changes nothing about any already-`completed` package's current status; it only changes what happens on *future* completions and *future* `needs_review` recovery attempts.

## Alternatives Considered

- **Root-cause the actual Make.com failure mechanism first**, before writing a detection-side fix. Attempted: pulled the live blueprint via the Make.com API (confirmed module 409 at `max_tokens: 6000`) and the execution log history for the exact failure window (all `status: success`). Couldn't go further — per-module execution bundle detail isn't exposed at this session's API access level. Rather than block the fix on an investigation with no clear next step, closing the gap at the layer this codebase already uses for exactly this purpose (ADR-0049) ships a real improvement now; the upstream mechanism remains an open question, not a blocker.
- **Bulk-remediate the 21 historical packages in the same pass.** Rejected: this is a materially different, bigger decision (real cost, customer communication for orders up to a year old, and no established precedent for what the right remedy even is at that age) than "stop it from happening again," which is what was asked. Flagged separately rather than folded in.
- **Include the accomplice branch in the blocking check for completeness.** Rejected for now — conditional on `has_accomplice`, not verified against the historical sweep, real risk of a false positive the evidence doesn't support yet.

## Consequences

- **Positive:** the exact failure signature that let two real, hours-old paid packages ship with silently empty round content (despite identity fields being fine) now blocks completion and triggers the existing auto-recovery re-fire, going forward.
- **DECIDED (2026-08-20): no remediation for the historical backlog.** Checked precisely: 0 of the 21 affected packages fall within the last 30 days — the newest is 2026-04-22, four months old. Jonathan's call: a mystery party that old has almost certainly already been played, so fixing the content now wouldn't help the customer who received it, and no one has complained. Proactive outreach was considered and explicitly declined — the party already happened either way, and reaching out risks manufacturing a complaint that doesn't exist. This closes the historical-backlog question; nothing further planned unless a specific customer raises it.
- **Not addressed — a real open question:** why Make.com's module 409 (or 509/513, historically) occasionally writes a character's round content as empty while reporting the run as successful, even with adequate token budget. This ADR closes the "ships undetected" gap, not the upstream cause.

## Addendum (2026-09-08): the deliberately-excluded accomplice branch turned out to be a real, live gap — closed with new evidence this ADR didn't have

This ADR's Decision and Alternatives sections both excluded `round*_accomplice`/`final_accomplice` from the check, reasoning the branch was "conditional on `conversations.has_accomplice`" and that including it risked false-positiving on characters who legitimately never get it — a reasonable call at the time, with no historical-sweep evidence either way for that specific field.

A routine purchase sweep ([ADR-0103 Addendum 31](0103-new-purchase-coherence-sweep-ritual.md#addendum-31-2026-09-08-two-accomplice-branch-content-gaps-found-and-fixed--plus-closed-the-detection-gap-that-let-them-ship-unalerted-and-a-language-blind-detector-mistake-caught-mid-investigation)) found a live customer package where 1 of 17 characters was missing the entire accomplice branch while all others had it — proving the assumption above wrong for `mystery_style='character'`: `conversations.has_accomplice` is reset by `validate_package_characters()` based on `character_role='accomplice'` being **pre-assigned**, which never happens in a slip-style game (roles are drawn at the table). The flag doesn't track whether the branch's *content* exists at all, so gating the check on it — the exact caution this ADR raised — would have been the wrong gate regardless.

The fix that ADR-0103 Addendum 31 shipped uses a different gate than either this ADR considered or its own first attempt tried: **peer-existence within the same package** (if any other character has the field populated, an empty one on a peer is a real gap) rather than `has_accomplice` or an English-keyword match against `detective_script` (the latter was tried and found to silently fail on non-English packages — see that addendum for the Spanish-language case that exposed it). This closes exactly the gap this ADR's Alternatives section flagged as "real risk of a false positive the evidence doesn't support yet" — the evidence now exists, and the gate design sidesteps the false-positive risk by construction rather than needing a bigger historical sweep to justify a `has_accomplice` join.

Also closed in the same migration: `reveal_confession_guilty`/`reveal_confession_accomplice` were never checked by this function for any character, any style — not a deliberate exclusion, just never added. Same peer-existence gate; see the addendum for detail and the corpus-wide sweep results (confirmed the pre-existing historical backlog this ADR already decided not to backfill is unchanged in scope, not enlarged).

Not widened here: the matching auto-heal re-fire in `notify-generation-issue` this ADR's Decision paired with its own detection change. Deliberately alert-only for the new check for now — see the linked addendum for why.
